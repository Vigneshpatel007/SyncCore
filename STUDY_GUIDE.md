## 1. The big picture (say this first)

SyncCore is a **three-tier web application**:

```
 Browser (React)  ──HTTP + JSON──▶  Spring Boot REST API  ──JPA/Hibernate──▶  MySQL
 what the user sees                  business rules + security                  permanent storage
```

Inside Spring Boot there are four layers. A request always travels **down** and the answer travels **back up**:

```
Controller  →  Service  →  Repository  →  Database
(HTTP door)    (rules)     (SQL access)    (tables)
```

| Layer | Job | Example in this project |
|---|---|---|
| **Controller** | Receives the HTTP request, calls a service, returns JSON. No business logic. | `OrderController` |
| **Service** | Business rules: "is there enough stock?", "calculate the total". | `OrderService` |
| **Repository** | Talks to MySQL. Spring writes the SQL for you. | `OrderRepository` |
| **Entity** | A Java class that represents one database table. | `Order`, `Product` |

**Why layers?** Each part has one responsibility, so the code is easy to test, change and scale. This is the
"layered architecture" in your abstract.

## 3. Backend explained, file by file

### 3.1 Entities: tables as Java classes (`entity/`)
```java
@Entity @Table(name = "products")
public class Product {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;   // primary key, auto-increment
    @ManyToOne @JoinColumn(name = "supplier_id") private Supplier supplier;     // foreign key
    @Column(nullable = false, unique = true) private String sku;
    private BigDecimal unitPrice;                                               // BigDecimal for money
}
```
- **`@Entity`**: Hibernate maps this class to a table. With `ddl-auto=update` it **creates the tables for you**.
- **`@Id` + `@GeneratedValue`**: primary key generated by MySQL (auto-increment).
- **Relationships** (from your ER diagram):

| Annotation | Meaning | Where |
|---|---|---|
| `@ManyToOne` | many rows → one row | Product → Supplier, Order → Customer, OrderItem → Product |
| `@OneToMany` | one row → many rows | Order → OrderItems |
| `@OneToOne` | one row ↔ one row | Employee ↔ User, Inventory ↔ Product |

- **Lombok** (`@Getter @Setter`) generates getters/setters at compile time so entities stay short.
- **`@JsonIgnore`** on `User.passwordHash` guarantees the hash is never sent to the browser. On `OrderItem.order` it prevents an infinite JSON loop.

### 3.2 Repositories: database access without SQL (`repository/`)
```java
public interface ProductRepository extends JpaRepository<Product, Long> {
    boolean existsBySku(String sku);   // Spring generates: SELECT COUNT(*) ... WHERE sku = ?
}
```
Extending `JpaRepository` gives `save`, `findAll`, `findById`, `delete`, `count` for free. Method names are parsed
by Spring Data (`findByUsername`, `existsByEmail`). For reports we use **JPQL** with `@Query`, for example
grouping sales by date with `sum()` and `group by`.

### 3.3 DTOs: what the client is allowed to send (`dto/`)
A DTO (Data Transfer Object) is a small class (here a Java `record`) that carries data in or out.
`ProductRequest` has validation annotations:
```java
@NotBlank String name,
@DecimalMin("0.01") BigDecimal unitPrice
```
**Why not accept the entity directly?** A client could send fields it must not control (like `id` or a role).
A DTO whitelists exactly what is allowed. (`Customer`/`Supplier` are simple enough that they carry their own validation.)

### 3.4 Services: business logic (`service/`)
The most important method is `OrderService.createOrder`:

1. Load the customer, find the logged-in employee from the token's username.
2. For **each line**: load the product and its inventory record.
3. **Business rule:** if `stock < requested` → throw `BusinessException` (HTTP 400 with a clear message).
4. Reduce the stock, copy the current price into the order item, add to the running total.
5. Save the order. `cascade = ALL` also saves its items.

```java
@Transactional
public Order createOrder(...)
```
**`@Transactional`** makes the whole method **all-or-nothing**. If line 3 of an order fails, the stock reductions of
lines 1 and 2 are rolled back automatically. This keeps stock and revenue consistent (the exact problem in your abstract).

**Dependency Injection:** services never write `new ProductRepository()`. They declare it in the constructor and Spring supplies it:
```java
public ProductService(ProductRepository repo, ...) { this.repo = repo; }
```
This makes code loosely coupled and easy to test with mocks.

### 3.5 Controllers: REST endpoints (`controller/`)
```java
@RestController @RequestMapping("/api/customers")
public class CustomerController {
    @GetMapping            public List<Customer> all()                       // READ
    @PostMapping           public ResponseEntity<Customer> create(@Valid @RequestBody Customer c)  // CREATE
    @PutMapping("/{id}")   public Customer update(@PathVariable Long id, ...) // UPDATE
    @DeleteMapping("/{id}") @PreAuthorize("hasRole('ADMIN')") ...             // DELETE
}
```
| Annotation | Meaning |
|---|---|
| `@RestController` | Returns JSON, not HTML pages |
| `@RequestBody` | Convert the JSON body into a Java object |
| `@Valid` | Run the validation annotations first |
| `@PathVariable` | Take `{id}` from the URL |
| `ResponseEntity` | Lets us choose the HTTP status (201 Created, 204 No Content) |

HTTP verbs ↔ CRUD: **GET**=Read, **POST**=Create, **PUT**=Update, **DELETE**=Delete.

### 3.6 Exception handling (`exception/GlobalExceptionHandler.java`)
`@RestControllerAdvice` is one central place that catches exceptions from every controller and returns a clean JSON error:

| Exception | HTTP status | Meaning |
|---|---|---|
| `MethodArgumentNotValidException` | 400 | `@Valid` failed (field-by-field messages) |
| `BusinessException` | 400 | e.g. insufficient stock |
| `BadCredentialsException` | 401 | wrong username/password |
| `AccessDeniedException` | 403 | logged in, but role not allowed |
| `ResourceNotFoundException` | 404 | id not found |
| `DataIntegrityViolationException` | 409 | duplicate SKU/email, or deleting something still in use |

The React forms read the `errors` map and show each message under the right input.

### 3.7 Performance and monitoring (Unit 8)
- **Caching:** `ReportService.summary()` is `@Cacheable("dashboard")`. The first call queries MySQL; later calls come from memory. `@CacheEvict` on `createOrder`, `cancel` and inventory updates clears it so numbers never go stale.
- **Logging:** `OrderService` logs every order with SLF4J. The log format is set in `application.properties`.
- **Actuator:** `/actuator/health` and `/actuator/metrics` expose application health and performance numbers.

### 3.8 Swagger / OpenAPI
Open `http://localhost:8080/swagger-ui.html`. It lists every endpoint automatically. Log in via `POST /api/auth/login`, copy the
token, click **Authorize**, paste it, and you can test every API (this replaces Postman).

## 4. Security: JWT and Spring Security (the part faculty usually asks)

### 4.1 What is JWT?
**JWT = JSON Web Token.** After you log in successfully, the server gives the browser a small signed string. The browser
shows that string on every later request, which proves "I already logged in".

A JWT has three parts separated by dots:

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJBRE1JTiIsImV4cCI6...  . 8kX2...
      HEADER                              PAYLOAD (claims)                    SIGNATURE
   algorithm = HS256        {"sub":"admin","role":"ADMIN","exp":1760000000}    HMAC-SHA256(header+payload, SECRET)
```

- **Payload:** who you are (`sub` = username), your `role`, and when it expires (`exp`). It is only Base64-encoded, **not encrypted**, so never put passwords in it.
- **Signature:** created with a **secret key that only the server knows**. If anyone edits the payload (for example changes `EMPLOYEE` to `ADMIN`), the signature no longer matches and the server rejects the token.

**Analogy:** a wristband at a concert. Security checks your ticket once at the gate (login) and gives you a tamper-proof wristband (JWT).
Inside, staff only look at the wristband (token), not your ticket (password) again.

### 4.2 Stateless authentication
The server stores **no session**. Everything needed (user and role) is inside the token. Benefits: the server scales easily
(any server instance can verify the token) and there is no session memory to manage. (`SessionCreationPolicy.STATELESS` in `SecurityConfig`.)

### 4.3 Authentication vs Authorization
- **Authentication** = *who are you?* (login: username + password)
- **Authorization** = *what may you do?* (role checks: Admin vs Employee)

### 4.4 The login flow, step by step
```
1. React  ─ POST /api/auth/login {username, password} ─────────────▶ AuthController
2. AuthService calls AuthenticationManager.authenticate(...)
3.   └▶ CustomUserDetailsService loads the user from MySQL
4.   └▶ BCrypt compares the typed password with the stored hash  (wrong? → 401)
5. JwtUtil.generateToken(username, role) builds + signs the JWT
6. Server ─ { token, username, role } ─────────────────────────────▶ React
7. React saves the token in localStorage (AuthContext.login)
```

### 4.5 What happens on every later request
```
1. Axios request interceptor adds the header:   Authorization: Bearer <token>
2. JwtAuthFilter (runs before the controller):
      read header → jwtUtil.isValid(token)? → read username + role → tell Spring Security "this request is user X with ROLE_Y"
3. SecurityConfig rules: URL needs authentication?  (/api/auth/login is public, everything else is not)
4. @PreAuthorize("hasRole('ADMIN')") on the controller method checks the role
5. Controller runs. If the role is wrong → 403 Forbidden. No/invalid/expired token → 401 Unauthorized.
```

### 4.6 The security classes
| Class | What it does |
|---|---|
| `JwtUtil` | `generateToken()` signs a token; `parse()`/`isValid()` verify signature + expiry using HMAC-SHA256 and the secret from `application.properties` |
| `JwtAuthFilter` | A filter (`OncePerRequestFilter`) that reads the Bearer token on each request and puts the user into `SecurityContextHolder` |
| `CustomUserDetailsService` | Teaches Spring Security how to load a user from **our** `users` table |
| `SecurityConfig` | The rulebook: public URLs, stateless sessions, where our filter sits, BCrypt bean, CORS |
| `@PreAuthorize` | Method-level role check (enabled by `@EnableMethodSecurity`) |

### 4.7 Password hashing with BCrypt
Passwords are **never stored as text**. `passwordEncoder.encode("admin123")` produces something like
`$2a$10$N9qo8uLO...`.
- **One-way:** you cannot turn the hash back into the password.
- **Salted:** a random salt is mixed in, so the same password gives a different hash every time (defeats rainbow tables).
- **Slow on purpose:** makes brute-force guessing expensive.
At login Spring hashes the typed password with the stored salt and compares the two hashes.

### 4.8 Frontend side of security
- **`AuthContext`** stores `user` and `token`, exposes `login`, `logout`, `isAdmin`.
- **`ProtectedRoute`** redirects to `/login` if not logged in, and away from admin-only pages for employees.
- **Axios interceptors** (`api/axios.js`): the *request* interceptor attaches the token automatically; the *response* interceptor logs the user out when the server returns 401 (expired token).
- **Important point to say aloud:** hiding a menu item or blocking a route in React is only for user experience. A user could still call the API manually. The **real** protection is on the backend (`@PreAuthorize`, the JWT filter). Try it: log in as `staff` and call `GET /api/reports/summary` in Swagger → `403`.

### 4.9 Honest trade-offs (shows depth)
- **localStorage vs httpOnly cookie:** localStorage is simple but readable by JavaScript, so an XSS bug could steal the token. React escapes output by default, which reduces that risk. Production systems often use httpOnly cookies or short-lived access tokens plus refresh tokens.
- **Why CSRF is disabled:** CSRF attacks rely on the browser *automatically* sending cookies. We send the token manually in a header, so that attack does not apply.
- **Secret key:** `JWT_SECRET` must be long (32+ characters) and kept out of source code in production (environment variable).
- **Token expiry:** set to 24 hours (`app.jwt.expiration-ms`). A token cannot be revoked before it expires unless you add a blacklist.

### 5.2 `useFetch`: the data-loading pattern
```js
const [data, setData] = useState([]);   // the result
const [loading, setLoading] = useState(true);
const [error, setError] = useState('');
useEffect(() => { load(); }, [load]);   // runs once when the page opens
```
Every page shows **loading → error (with a Try again button) → empty message → data**. That is the retry logic / performance UX from Unit 8.

### 5.3 `CrudPage`: the reusable component (best thing to show)

- **Add / Edit modal** with client-side validation, then `POST` or `PUT`
- **server-side validation errors** shown under each field
- **Delete confirmation** modal (and a clear message if the server refuses with 409)

If faculty ask "what is reusability?", open `Products.jsx` (about 30 lines) and show that it only describes *what* differs.

### 5.4 The Orders screen
Choose a customer, add product lines, see the live total, and a warning if quantity exceeds stock. On save it calls
`POST /api/orders`; the **server** re-checks stock (never trust the browser). The details dialog shows the order lines and a
**Cancel order and restore stock** button.

## 6. One feature end to end: "Create an order"
1. User clicks **Save sale** in `Orders.jsx` → `api.post('/orders', {customerId, items})`.
2. Axios interceptor adds `Authorization: Bearer <JWT>`.
3. `JwtAuthFilter` validates the token and sets the user.
4. `OrderController.create` runs; `@Valid` validates the `OrderRequest` DTO.
5. `OrderService.createOrder` (transaction starts): loads customer/product/inventory, **checks stock**, reduces stock, builds the order, computes the total.
6. `OrderRepository.save` → Hibernate generates the `INSERT` statements for `orders`, `order_items` and the `UPDATE inventory`.
7. Transaction commits. The dashboard cache is evicted. The saved order is returned as JSON (201).
8. React closes the dialog and reloads the list. If anything failed, the error message appears in the dialog and **nothing** was saved.

## 7. Likely viva questions, with short answers

**Q1. Why Spring Boot?** It removes boilerplate configuration: embedded Tomcat, auto-configuration, and starters for web, JPA and security.

**Q2. What is MVC? Where is it in your project?** Model-View-Controller. Model = entities, View = the React UI (JSON in between), Controller = `@RestController` classes. Services and repositories sit behind the controller.

**Q3. What is REST?** An API style using HTTP verbs on resource URLs (`GET /api/products`), stateless, exchanging JSON.

**Q4. What is JPA vs Hibernate?** JPA is the specification (annotations and interfaces). Hibernate is the implementation that generates the SQL. Spring Data JPA adds the repository interfaces on top.

**Q5. What does `@Transactional` do?** Groups database operations into one unit: all succeed or all roll back. Used so an order never saves without its stock update.

**Q6. What is dependency injection?** Spring creates objects and supplies them through constructors, so classes do not create their own dependencies.

**Q7. Why DTOs?** To control exactly what comes in and goes out, apply validation, and avoid exposing entities or sensitive fields.

**Q8. What is JWT and why use it?** Signed token proving identity; allows stateless authentication (see section 4).

**Q9. Can a user edit their JWT to become admin?** No. The role is in the payload, but the signature is made with the server's secret. Any change invalidates the signature and the filter rejects it.

**Q10. Difference between 401 and 403?** 401 = not authenticated (no/invalid/expired token). 403 = authenticated but not permitted for that action.

**Q11. Why BCrypt and not SHA-256 or plain text?** BCrypt is salted and deliberately slow, which defends against rainbow tables and brute force. Plain text would expose every password in a breach.

**Q12. Where is the JWT stored and is that safe?** `localStorage`. It is simple but vulnerable if XSS exists; production alternatives are httpOnly cookies / refresh tokens (section 4.9).

**Q13. What is CORS?** Browser rule blocking a page from calling a different origin. `SecurityConfig` allows our front end's origin. In development the Vite proxy avoids the issue.

**Q14. What does `ddl-auto=update` do?** Hibernate creates or alters tables to match the entities. Fine for development; production often uses migrations (Flyway).

**Q15. Why is the `orders` table named that way?** `ORDER` is a reserved SQL keyword.

**Q16. Why `BigDecimal` for prices?** `double` has binary rounding errors (0.1 + 0.2 ≠ 0.3). `BigDecimal` is exact.

**Q17. Why copy `unitPrice` into `order_items`?** Prices change. Storing the price at sale time keeps old invoices correct.

**Q18. How does the system prevent overselling?** `OrderService` checks inventory inside a transaction and throws a `BusinessException` if stock is too low. (Limitation: for very high concurrency you would add optimistic locking with `@Version`.)

**Q19. How is caching handled and what is its risk?** `@Cacheable` stores the dashboard summary in memory; `@CacheEvict` clears it when orders or stock change. The risk is stale data if you forget to evict.

**Q20. How did you test?** Unit tests with JUnit 5 and Mockito mock the repositories and verify the stock rule; Swagger/Postman for API testing; manual UI testing by role.

**Q21. What is Docker Compose doing here?** Starts three containers (MySQL, Spring Boot, nginx serving React) with one command, with the backend waiting for MySQL's health check.

**Q22. What is a React error boundary?** A component that catches rendering errors in its children and shows a fallback UI instead of a blank page.

## 8. A 5-minute demo script
1. **Login page:** point to the four-step flow (it matches Fig. 1 of your abstract). Log in as `staff`.
2. Show the sidebar: no *Employees* or *Reports*. Open **Products**, add a product, show a validation error (empty price).
3. Open **Inventory**: the pens show **Reorder now**.
4. **Orders → New order:** try quantity larger than stock, see the warning/error. Save a valid sale. Open **Inventory** again: stock reduced.
5. Open the order → **Cancel order and restore stock** → stock returns.
6. Log out, log in as `admin`: show the **Dashboard KPIs**, **Reports**, **Employees** (create an employee, explain BCrypt).
7. Open **Swagger**: call `GET /api/reports/summary` without a token (401), with the staff token (403), with the admin token (200). This proves backend-enforced security.
